`casts` is a personal podcast manager for multi-device use.

The best way to introduce this project is to view it as the confluence of my interest in multiple topics: cross-platform app-data promulgation for a given application, graphql, event sourcing and CRDTs, my love of macOS/iOS user interface design, and my daily enjoyment of podcasts.

Simply put, I was frustrated with the difficulty of keeping track of which podcasts I was listening to, which I had already listened to, which I wanted to archive and keep audio data files around for, etc. The existing solutions were either buggy, didn't offer syncing, or only worked on a subset of the idiosyncratic platforms I work on (namely, macOS, Linux, and FreeBSD). Needing a project anyway to keep up my skills, I decided to over-engineer my own solution. I went with embedding the application logic as a GraphQL application inside a native runtime serving a native interface, which changes synced peer-to-peer as CRDTs modifying a distributed stream of events backing the user's view of the podcast library. Modeling the application state as an event store means the backing store can be fulfilled by many different storage engines, like both DynamoDB, Sqlite, CouchDB, and Redis. Combined with GraphQL, this means native applications need only to write presentation code for the underlying graphql app, and the rest of the application logic might be shared cross-platform. Modeling the events as CRDTs ensures that application state can be synced between nodes—say, between a mobile client and a server—and using GraphQL as the interface into this ensures that I can easily generate native bindings in a command-query separation-friendly interface. Finally, I implemented this in Rust so that the GraphQL bindings might be embedded in-memory in any libc-based runtime (and a little extra elbow grease in redirecting the client in-memory rather than to an http or websocket destination).

So, as a summary, here are the components:

1. A [commit store](https://git.sr.ht/~duane/casts/tree/main/item/commit-store), backed by [postgresql](https://git.sr.ht/~duane/casts/tree/main/item/commit-store/src/postgres.rs) or [sqlite](https://git.sr.ht/~duane/casts/tree/main/item/commit-store/src/sqlite.rs), but I've spiked a dynamodb and rocksdb binding as well. This accepts commits to a given stream and allows subscribing to long-lived connections that stream updates for a given stream. This resolves conflicts by enforcing that each commit writes at most one version on top of the current stream's version, or it's rejected. This exports both a native rust API and a [GRPC2 binding](https://git.sr.ht/~duane/casts/tree/main/item/commit-store/src/grpc.rs). This comes with a [dispatcher](https://git.sr.ht/~duane/casts/tree/main/item/commit-store/src/dispatch.rs) that maintains long-lives subscriptions.
2. A graphql application [schema](https://git.sr.ht/~duane/casts/tree/main/item/casts/src/graphql/mod.rs) and [http server](https://git.sr.ht/~duane/casts/tree/main/item/casts/src/bin/casts-server.rs), which translates the [commands](https://git.sr.ht/~duane/casts/tree/main/item/casts/src/commands/feed_aggregate_command.rs) into [events](https://git.sr.ht/~duane/casts/tree/main/item/casts/src/events/feed_aggregate_event.rs) and the events into an [aggregate](https://git.sr.ht/~duane/casts/tree/main/item/casts/src/aggregate/feed_aggregate.rs), which represents the application state in a friendly manner.
3. A set of [libraries and tools](https://git.sr.ht/~duane/casts/tree/main/item/casts-c) that generate bindings to allow the [Apollo iOS client](https://www.apollographql.com/docs/ios/) to [call seamlessly](https://git.sr.ht/~duane/casts/tree/main/item/casts-ios/casts-swift/Sources/Client/EmbeddedClient.swift) into an embedded version of the graphql library.
4. A front-end client[] that accepts user input, shows application state, and allows playing of the episodes in a standard podcast interface.
5. A [macOS/iOS app to read the commit-store](https://git.sr.ht/~duane/casts/tree/main/item/commit-store-macos) for debugging purposes.


Components 1-3 are represented both as servers in their own right and embedded components of the local, native app. Changes are synced by serializing CRDT-based changes, so mobile apps will continue functioning fully without a connection to an upstream server, and any conflicts will not require user intervention. It's also highly scalable—from a server perspective, the commit store servers are highly horizontally scalable, and the backing store can even be separate for *every stream*, which is basically an optimal scenario for sharding. The simplicity of the core functionality—a commit store capable of serializing commits consistnently and dispatching commits for further processing—is capable of fitting around other application paradigms. For instance, it might not make sense to model tracking the play state as a series of events—many events when you really just want the last-played state—but it would make sense for a tracking process to emit an event for when an episode has been started or fully listened to or when they stopped listening midway through an episode

That said, it's important to note that this is a work-in-progress, and I'm currently implementing[] the in-memory stream subscription interface.

I hope this suffices for a broad explanation. For more of technical look at why I developed this at all, what I'm working on now, and known problems, see https://man.sr.ht/~duane/casts. If you have questions, please reach out to duane@duane.cc.
